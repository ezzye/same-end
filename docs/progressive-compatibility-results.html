Same End · 24 October 2026 · Playback and robustness

Older-iPad picture fault isolated and corrected locally.

Release held while older-iPad sound acceptance remains unverified.

What caused the picture error

On a provider-reported physical iPad Pro 12.9 (2020), iOS 14, the fully downloaded fragmented MP4 failed with format error 4. A conventional MP4 containing the same compressed media was readable. The identical conventional file also failed with the long codec-qualified file type, but played when labelled simply video/mp4. Both faults occur after download; more network buffering cannot correct them.

What changed

Verified pieces are assembled locally into conventional MP4 windows of up to 16 seconds. Sample tables describe their timing; small, bounded capture overlaps are resolved without discarding or re-encoding compressed samples. Configuration changes stop a window, and even one supported piece can be converted. Native file playback uses the simple container type. Original signed media and peer forwarding are unchanged.

The current code remains on fix/buffered-compatibility. The live site and separate robustness source branch have not been changed.

Evidence and its limits

Physical iPad controls played generated 720p moving video after conversion, without the earlier format errors. The full player also produced advancing pictures. The final fully buffered run supplied all 12 pieces before playback, reported 621 decoded frames, no dropped frames or format errors, and three file loads over roughly 22 seconds. Maximum measured programme drift was 0.735 seconds.

Chrome Normal, Full room and Picture only passed picture, decoded tone and timing; maximum measured drift was about 0.20 seconds. Native compatibility testing reduced file loads from eleven to three over about twenty seconds in the earlier paired Chrome run. All 137 general automated checks passed. The final physical summary is saved in the accompanying JSON evidence.

This is not yet a physical iPad sound pass. Its automated taps did not unlock audio; the AudioContext stayed suspended. Local headless WebKit also gave poor frame-callback cadence and no analyser tone, so it is not used as Apple acceptance. A genuine device tap and sustained picture/sound check are still needed before deployment. Short generated tests do not establish full-match or family-network reliability.

Robustness next

The separate branch is feat/relay-selection-repair, commit 5ddc331. Its four focused suites passed all 32 checks in this review. Both real-WebRTC qualification cases passed: changing away from a slowed supplier and repairing a missing piece from another peer. Post-change maximum frame gaps were 67 ms and 84 ms, with decoded tone and clock drift below 40 ms. This did not exercise the extra third direct viewer. These checks do not replace the longer comparison.

The strongest next candidate is to stop admitting a measured weak laptop as a supplier. Test that separately from the original host taking one extra direct viewer, which consumes more host upload capacity. Keep missing-piece repair separate until its newcomer behaviour is measured.

The earlier full comparison still supports holding deployment: both features together reduced terminal-viewer freezing from about 35.3 to 32.6 seconds, while severe gaps remained. The later weak-supplier fix has only one partial comparison. Complete two same-build repeats each of off/off, selection only, repair only and both together, measuring new arrivals, decoded picture and sound, drift, freezes and host upload. Do not accept a newcomer regression or severe multi-second gaps.
