How Same End builds a private video delivery tree, carries standard HLS through its peers, and turns verified bytes into synchronised picture and sound.

Current implementationInline diagramsWorked figuresNo external assets

Same End has a persistent room, a discovery overlay and a video delivery tree. They have different jobs and lifetimes. Understanding them separately explains why chat can work without a source, why a peer connection may not produce a picture, and why a large buffer cannot fix every playback problem.

01 · Follow the bytes

Standard media, private delivery.

The capture computer is both the source and a viewer of the delayed programme. It captures a chosen tab, encodes one continuous H.264/AAC timeline and packages it as HLS/CMAF. Other computers verify and forward the original source’s bytes; they do not record their own delayed player again.

Room & chat

Who can join?

An encrypted room record holds the current invitation, source presence and diary. The small HTTPS service stores encrypted state and chat. A room can exist before capture and after it stops.

Discovery overlay

Who can connect?

WebSocket trackers introduce WebRTC peers. STUN helps discover reachable addresses. Several authenticated contacts may exist without carrying the programme.

Delivery tree

Who supplies whom?

Each viewer chooses one upstream supplier. A device can normally supply two children. Application messages carry source-signed video over the selected peer wires.

The magnet is the bootstrap.

It identifies a small encrypted descriptor torrent and includes its private key. The ongoing match is not a growing ordinary BitTorrent video file. Same End uses a custom WebTorrent extension over WebRTC for live media; a normal torrent player cannot join this programme.

Implementation: room links, descriptor publishing, continuous source.

02 · The shape of the network

A tree inside a wider set of contacts.

The selected media routes form a source-rooted tree. A viewer can also become a relay: it receives one stream and uploads copies to children. A leaf need not upload video until a child is assigned. Phones may forward as viewers too; hiding phone capture does not make every phone a permanently leaf-only node.

This is an illustration of permitted outcomes, not an exact simulation or a readout of your room. In practice peers arrive, exchange status and compete for available slots asynchronously. A healthy connected viewer is not continuously moved to the mathematically “best” parent.

What the tree saves

The source can reach more people without uploading a separate copy to everyone. In an ideal fully populated binary tree, total participants grow as 1 → 3 → 7 → 15 over successive levels, including the source. Those are tree positions, not a tested group-size promise.

What it still costs

Every parent–child edge is a separate upload and download. Relays need spare upload, memory, CPU and a browser that keeps running. A deep path adds failure points and transport latency even though the configured group delay stays the same.

Application-layer replication, rather than IP multicast.

The laptops copy data on their own unicast peer links. IP multicast uses group-address forwarding in supporting networks and routers. A browser app cannot turn an arbitrary collection of home and mobile connections into an ISP multicast service. Same End does not implement IP multicast.

Implementation: rooted ancestry, 12 discovery wires, application peer cap. Background: IP multicast model, RFC 1112.

03 · The formation algorithm

Joining is a sequence of gates.

  1. Open the persistent room.

    The private fragment supplies the room identity and secret. The browser removes the visible fragment, authenticates the read request and decrypts the room state locally. Chat can open immediately. No current source means a waiting room, not a failed room.

  2. Resolve the current capture.

    The encrypted room record supplies its current magnet. That magnet identifies the descriptor torrent and a separate 32-byte cast secret. A source restart publishes a new capture behind the same room invitation.

  3. Find and establish possible peer links.

    The pinned WebTorrent client uses configured WSS trackers and WebRTC. ICE checks possible direct paths; STUN assists address discovery. There is no configured TURN fallback, no browser DHT and no HTTP video fallback.

  4. Pass two independent trust gates.

    Download and AES-GCM-authenticate the small descriptor; validate its configuration and source public key. Separately, each candidate wire proves possession of the shared cast secret with HMAC challenges. These operations are asynchronous; neither alone establishes playable media.

  5. Find an eligible supplier and reserve a slot.

    The viewer must have no current parent or outstanding parent request. It examines authenticated status for a source-rooted, clock-ready peer with spare downstream capacity, a permitted path length and no ancestry loop or active cooldown.

  6. Commit the parent–child relationship.

    _pc_offer requests supply; _pc_accept reserves it; the requester opens and sends _pc_confirm. The supplier rechecks its reservation and capacity before opening its side. A race can still produce a rejection and another search.

  7. Start the application session.

    The application hello negotiates receipts/resume. Ping/pong establishes source-clock offset. Only correctly signed media enters the caches. The player then waits for its group target and required decodable files.

How a candidate wins

The one-second maintenance scan sorts shorter advertised ancestry first. Incoming status can also trigger an immediate attempt. There is only one outstanding parent request, so the first eligible attempt that succeeds establishes the parent.

This favours short routes when the scan has choices. It is not a guaranteed shortest-path tree, global bandwidth optimisation, geographic ranking or continuous load balancing.

How a loop is rejected

Suppose C receives through A. C advertises an ancestry containing S and A. If A tries to receive through C, it sees its own identity in C’s ancestry and rejects that path. An orphan’s cached bytes do not let it claim a rooted live source.

04 · Names, messages and trust

A stack of protocols, each with a job.

“P2P”, “HLS” and “encryption” describe different layers. The video travels as application data on WebRTC data channels, not as a normal WebRTC audio/video track sent directly to a video element.

MechanismWhat it establishesWhat it does not establish
Room AES-GCM + access tokensThe room/chat payload is encrypted before storage. Read/write credentials have different roles.An anonymous network: the service still sees room identifiers, request metadata and ciphertext sizes.
Cast AES-GCM descriptorOnly someone with the cast secret can open and authenticate the encrypted configuration.A video connection, successful capture or current source availability.
HMAC-SHA-256 challengeA peer wire knows the shared cast secret.A named person’s identity or authority to generate source-signed video.
WebRTC / DTLSEncrypted transport between two connected peers.Confidentiality from invited relays: each participating relay can access the bytes it handles.
SHA-256 + ECDSA P-256Each accepted piece matches its signed hash, source identity, epoch, programme and interval.That the source picture is smooth, audible, correctly licensed, or aligned with another independent recording.

Invitations are bearer credentials: whoever holds a usable invitation can share it onwards. The normal flow keeps secrets in URL fragments and removes those fragments before ordinary requests; it is not an anonymity system or a public-key identity directory. Peer networking can expose addresses to peers and introduction services.

The two message layers and the source-signed record

The transport uses _pc_hello, _pc_auth, _pc_ready, status and offer/accept/confirm/reject messages. On an admitted media adapter, the engine uses a different hello, clock ping/pong, segment metadata, binary slices, receipts and departure messages.

// Canonical v2 array signed by the source, in this order:
[2, cast, sourceId, sourceEpoch, programId, programStartTime,
 alignmentVersion, seq, start, duration, size, mime, hash]

The source private signing key stays in its browser runtime; the descriptor carries the verification public key. A relay forwards the original signed record. Changing bytes, identities or timing breaks validation. Reassembly, hash/signature checks and interval checks occur before player use and onward caching.

Extension control JSON is limited to 4 KiB. The media adapter frames strings and binary data with a type byte and limits a payload to 64 KiB; the engine normally divides an envelope into 16 KiB binary slices. Those slices are not HLS segments.

Implementation: room cryptography, descriptor encryption, extension framing, canonical signature, media acceptance. Background: WebRTC data-channel stack, ICE, browser WebTorrent.

05 · Capture and packaging

One continuous programme, split for delivery.

The host requests a tab capture around 1280 × 720, ideally 25 fps, with audio when supported. Where its required APIs exist, the normalizer converts actual pixels to a stable 1280 × 720 sRGB/BT.709 shape and drops excess frames to a nominal 25 fps cadence; otherwise it passes the original track through. Neither path can invent missing input frames.

WebCodecs and Mediabunny 1.62.1 then maintain a continuous H.264/AAC encoding timeline. The default video target is 1.5 Mbit/s, with 0.8 and 3 Mbit/s choices; audio targets 96 kbit/s when included. Targets are not measured output rates. There is currently one selected video quality, not an adaptive ladder offering each viewer its own rendition.

What the manifest tells a player

The master identifies media playlists. A media playlist supplies sequence numbers, segment durations, paths and initialization information. A player can find the files needed around its intended position without treating each segment as a new standalone film.

Illustrative media playlist, not captured output:

#EXTM3U
#EXT-X-TARGETDURATION:2
#EXT-X-MEDIA-SEQUENCE:150
#EXT-X-MAP:URI="init-0.mp4"
#EXTINF:2.000,
segment-0-150.m4s
#EXTINF:2.000,
segment-0-151.m4s

What Same End adds

The envelope groups current playlists, initialization files and newly completed media, with a source-relative interval. It has a 4 MiB ceiling, up to 24 files and a 64 KiB index ceiling. Safe local paths and allowed resource tags prevent a playlist from redirecting the player to arbitrary internet media.

Source packaging retains 180 completed segments in its live playlist window. Segment completion, not network slice arrival, determines when new packaged media becomes available.

HLS versus DASH versus Apple.

This path generates HLS, not DASH MPD manifests. H.264/AAC are codecs; CMAF is the fragmented media packaging; HLS is the playlist and streaming model. Native Apple HLS and hls.js can interpret the same source files. Same End does not need a proprietary Apple replacement for those files, but browser integration, codec availability and playback policies still differ.

Legacy captures remain on the old MediaRecorder/compatibility path. A fresh source created by the updated app uses the HLS profile; keeping an old capture alive does not convert it in place. Continuous packaging addresses a demonstrated class of boundary problems, but does not prove that every earlier glitch was a codec or packaging fault.

Implementation: pixel normalization and fallback, capture constraints, HLS/CMAF packager, envelope layout. Background: Mediabunny HLS output, HLS RFC 8216.

06 · Time, not just bytes

Everyone aims at the source’s clock.

The source creates a capture epoch. A viewer estimates the difference between its clock and the supplier’s source-adjusted clock using ping/pong timing. The supplier passes source time onwards; it does not give its children the time of its own delayed playback.

programme target (seconds)
= (local clock + estimated offset − source epoch) / 1000
− group delay

Offset estimation

If a request leaves at local 100.000 s and returns at 100.080 s, its midpoint is 100.040 s. A source-adjusted reply time of 100.540 s gives an estimated offset of +0.500 s.

The engine keeps the last ten valid samples and selects the lowest round-trip time; RTTs above seven seconds are rejected. Network asymmetry and multi-hop estimation still introduce error. This is not perfect clock synchronisation.

Position correction

The encoder’s startup timing maps media timestamps to the source-relative programme. Each HLS player aims at that mapped target. It runs at normal speed, with infrequent seeks for drift over 0.8 s and a 2.5 s correction cooldown.

Those thresholds are controller settings, not a promise that every device is always within 0.8 seconds. Hidden or suspended browsers may not execute on schedule.

At source programme time 600 s, a five-minute room aims at programme time 300 s. A late arrival aims at that existing group moment, which continues advancing while its cache fills; it starts when the current target has the required decodable media and need not impose a fresh five-minute wait on everyone. A new capture has a new epoch and its normal warm-up, even when the room link stays unchanged.

Implementation: clock exchange, encoder startup mapping, group target, HLS correction, native correction.

07 · Buffering explained

Five minutes of delay is not five minutes of playable reserve.

These stores sit at different stages. More bytes in one do not prove that another has the right decodable frame. The media stores are bounded browser memory, not durable hard-drive edge stores.

LayerPurposeCurrent bound / policy
Capture / packaging queueHold encoder output until complete files can be signed and handed to the engine.Backpressure guards include 16 MiB pending bytes, eight pending segments and a delivery timeout. If production cannot keep up, capture fails explicitly.
Signed relay reserveKeep verified source envelopes to play and supply other peers.192 MiB ceiling; pruning around the shared delay plus 30 s. Actual contiguous reserve is measured from the current play target and stops at a gap.
Verified player file cacheExtract verified playlists/init/segments for the chosen player.Active hls.js and native players each configure 32 MiB and a 60 s retention policy. The engine stages files from about target−4 s through target+16 s; player manifests expose available segments around target−24 s through target+12 s. These windows and ceilings do not guarantee 60 s of loaded future.
Decoder / media bufferPrepare playable media around the target.hls.js requests about 24 s, with a 36 s upper buffer target and 24 MiB byte setting. Browser behaviour varies; native buffering is browser-managed.

How files reach the player

MediaSource route

hls.js 1.7.3

A custom loader answers from the page’s verified file cache. The internal sameend.invalid namespace is a cache lookup, not an internet media host. hls.js parses playlists and appends media into the browser’s streaming buffer.

Native HLS route

Browser player + service worker

Where the compatible MediaSource route is unavailable, native HLS requests same-origin capability URLs. A service worker asks the owning page for verified bytes and returns a local response, including ranges. Video is not fetched from the site server or stored in persistent CacheStorage.

The native bridge needs HTTPS and service-worker support; a downloaded app HTML file alone cannot provide that bridge. Both routes still need compatible H.264/AAC decoding and a permitted sound-start gesture. A browser or OS name is not physical-device acceptance.

What a full buffer cannot repair

Missing or incompatible initialization, changing codec configuration, invalid timestamps, a blocked decoder, browser suspension or a muted source. If a healthy buffer drains because delivery stays slower than consumption, increasing it only postpones the stall. These require different diagnoses.

Implementation: relay retention, contiguous reserve, player feed, active hls.js cache and buffer settings, native cache, private worker responses. Background: hls.js platform requirements.

08 · Recovery without inventing future video

Repair the path; preserve the programme.

A departed relay and a vanished capture source are different failures. If the programme still exists upstream, a viewer can replace its supplier while preserving source identity, verified cache, player and clock. It resumes the group’s current moment rather than playing the interruption back later.

A supplier leaves or stalls

  1. Loss of the upstream wire starts a search. A separate watchdog also detects an open connection that stops delivering verified progress or control replies.
  2. The viewer applies a local 20 s cooldown to the failed supplier’s node identity. The viewer keeps its downstream children where possible and advertises its rooted state truthfully.
  3. A new authenticated rooted supplier passes the same admission checks. Resume hints skip a verified contiguous prefix instead of blindly resending everything.
  4. If useful reserve survives until new data arrives, playback may continue. Otherwise it waits and then rejoins the group target, potentially missing material.

The source disappears or restarts

  1. A verified source-signed end positively stops that capture. A relay cannot issue that end for the whole programme.
  2. A crash has no signed end. Existing cache may continue, but no peer can manufacture future source bytes.
  3. The independent room/chat remains. An expired 60 s owner lease means no recent source update, not proof of why it was lost.
  4. The saved organiser can publish a fresh source behind the same room link. Viewers follow it automatically, with a new capture epoch and warm-up.

MechanismCurrent policy
Stalled-source watchdogChecks about once a second, with a 12 s connection/progress grace. Responsive parents can receive bounded additional repair grace when children have sufficient reserve. A browser sampling gap resets grace.

These are independent timers, not a promised recovery deadline. ICE, discovery, browser suspension and media availability can dominate. Audio silence is deliberately excluded from supplier-failure decisions.

Why “connected” is not enough

A tracker reply proves introduction. A WebRTC connection proves a direct transport. HMAC proves membership. An ECDSA-verified envelope proves source-authored bytes. Only advancing decoded frames and audible output establish playback on that device.

09 · Numbers with assumptions

Spare upload is the resource the tree spends.

At the default targets, 1.5 Mbit/s video plus 0.096 Mbit/s audio gives about 1.596 Mbit/s encoded payload before repeated manifests/init files, protocol overhead, retransmissions and bitrate variation. The calculator is a planning model, not a speed test or the app’s admission algorithm.

For seven total participants in the illustrated full tree there are six video edges: aggregate payload transfer is roughly 6 × R. The source uploads 2R; the two forwarding viewers each upload 2R; each receiving viewer downloads R. The tree spreads upload across homes rather than eliminating the six copies.

Delivery receipts measure actual verified payload on a specific link over a recent window. They are not a maximum broadband-capacity test, and the current two-child policy does not calculate floor(upload / bitrate) and choose an arbitrary larger fanout. There is no automatic lower-quality rendition for a struggling viewer.

Units: Mbit/s and MB/GB here are decimal. Code memory ceilings use MiB (1 MiB =1,048,576 bytes). Encoded payload, signed-envelope size, decoder memory and total browser memory are different quantities.

Implementation: capacity advertisement, bounded receipts, encoder targets. All calculator figures are derived examples, not measured network results.

Two people watching the same match are not automatically backup sources.

Their ads, commentary, edits and broadcaster delays can differ. Equal wall clocks do not identify the same frame. Same End currently forwards one source’s exact signed bytes; independent backup requires an explicit trusted mapping between programmes and capture epochs.

The architectural gain is using established media packaging and players while retaining a private edge-delivery protocol. Remaining transport, capture, clock and decoder failures must still be measured separately. No direct-only design can guarantee a route through every carrier, firewall or VPN; a cached past cannot supply a missing future.

What the latest verification does and does not demonstrate

The source-free-room release recorded 248 unit/backend checks and isolated Chrome/WebKit room tests. A generated, signed WebRTC/HLS test included 95 seconds without a source, a 66-second source absence, a late join and restoration to three viewers. The maximum measured group spread in its sampled windows was about 0.176 s.

That is local controlled evidence, not a universal synchronisation guarantee, a physical-old-iPad acceptance result, a congested multi-home test, or 90-minute event stability. Reported Android 5G/VPN-off success on an earlier build is a separate owner observation; it should not be substituted for those missing checks.

Implementation boundary: backup helper, backup design. Latest release evidence: PR 28; controlled room scenario.

A compact glossary
Source
The browser capturing and signing the programme. It is the root of its current media tree.
Supplier / parent
The one peer a viewer currently receives video from.
Relay / child
A relay forwards received source bytes; a child receives from that relay.
Rooted
An advertised ancestry still leading to an active source path, rather than only an orphan’s saved cache.
Swarm / overlay
The WebTorrent peer-contact structure around the descriptor. It is wider than the selected delivery tree.
Magnet / infohash
A bootstrap identifier for the encrypted descriptor torrent, accompanied by a private cast key.
STUN / ICE / TURN
Address discovery; connectivity checking/selection; and an optional relay mechanism. No TURN server is configured in this app.
Codec
How picture or sound is compressed: H.264 and AAC on the new path.
CMAF / fMP4
Fragmented media packaging with initialization information and media fragments.
HLS manifest
A playlist describing media resources, ordering and timing. DASH uses a different manifest model; this app does not generate it.
Envelope / slice
A Same End signed batch of files, and the smaller messages used to transfer that batch.
Epoch
The time origin and identity context for one capture; a restart creates a new capture context.
Reserve
Contiguous verified media ahead of the current group target, rather than total bytes in memory.
Decoder buffer
The smaller browser media window being prepared for actual playback.
