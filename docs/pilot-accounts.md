# Pilot accounts

Anyone can read the inline fan forum and start or join private rooms without an account. A pilot account is for a lasting forum profile and private account feedback. It neither saves private room keys nor extends the existing room/club lifecycle. Forum participation additionally requires the organiser's pilot code and acceptance of the public forum rules.

Choose **Sign in / Create account** in section 3 beneath **Bring your mates**. The email/password provider opens in a separate account tab; the room remains in its original tab. Sign up, verify the emailed code, and return to the original tab after confirmation. Existing users can sign in or choose **Forgot your password?**. Passwords require at least 12 characters with uppercase, lowercase and a number. The public display name is chosen when joining the forum and can differ from the private email address.

A browser containing an older forum/feedback identity offers an explicit claim or a new profile. Claiming needs that browser's original secret and retains the fan ID, posts, feedback receipts, membership and any suspension. It consumes the old credential; names/emails cannot claim records. A different profile is never silently merged into an existing account. Lost unsigned browser secrets have no automatic recovery. Account ownership persists independently of 365-day content/receipt retention.

Tokens and PKCE transactions stay only in the original tab's memory. Code callbacks scrub their URL and relay no tokens, profile, room link or secret. Expected origin/window and random state protect opener messages; a random-state BroadcastChannel supports browser opener isolation. The parent exchanges its one-use code using its private PKCE verifier. The API gateway verifies JWT signature, issuer/client, time and custom scope; the backend checks fan purpose/claims, identity mapping and current participation status. Signout, expiry and account changes discard private results and pending response applicability. A reload needs sign-in again; the provider may retain its own SSO cookie. Logout does not clear another browser or a staff session, and already issued access JWTs can last up to one hour. Browser token decoding is presentation validation, not signature verification.

The fan pool supports self-signup, verified-email recovery, classic hosted UI and a public code-only client. The staff pool remains administrator-created with required TOTP MFA and its own client/issuer. The generic private-room routes remain unsigned. No production local-review credential or token fixture can authorize fan member routes.

The operator can suspend forum participation from the existing staff desk. Private feedback remains available to suspended users. Fan email/account removal during the pilot requires operator support; an automatic delete-account interface is not part of this release.

The initial deployment uses Cognito's default mail service. AWS currently limits that service to 50 email messages per day per AWS account; verification and recovery share the allowance. Review mail capacity before widening the pilot. No bulk invitations are sent by deployment. [AWS quotas](https://docs.aws.amazon.com/cognito/latest/developerguide/quotas.html), [authorization code and PKCE](https://docs.aws.amazon.com/cognito/latest/developerguide/authorization-endpoint.html).
